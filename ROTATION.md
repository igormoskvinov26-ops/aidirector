# Перевыпуск ключей после публичной утечки

**Статус: требуется действие владельца.**

Репозиторий `igormoskvinov26-ops/aidirector` публичный. До 11.09.2026 в нём
лежали в открытом виде:

| Где лежало | Что именно |
|---|---|
| `.env.example` (все коммиты) | партнёрский и пользовательский токены YCLIENTS, токен старого аккаунта, пароль PostgreSQL, пароль администратора |
| `rubl-director-v2 (2).zip` → `backend/scrape_salary.py` | **логин (телефон) и пароль от кабинета YCLIENTS** |

История переписана: значения заменены на `<REDACTED>`, архивы удалены из всех
коммитов. **Это не отменяет утечки.** Пока репозиторий был публичным, данные
могли быть скопированы автоматическими сканерами; GitHub какое-то время
сохраняет недостижимые объекты, доступные по прямой ссылке на SHA.
Единственная надёжная мера — перевыпуск.

---

## Порядок

| # | Что | Где перевыпускается | Что ломается на время замены |
|---|-----|--------------------|------------------------------|
| 1 | **Пароль кабинета YCLIENTS** | yclients.com → смена пароля + включить 2FA | вход в кабинет |
| 2 | `ADMIN_PASSWORD` | `openssl rand -base64 18` | вход в дашборд |
| 3 | `POSTGRES_PASSWORD` | `openssl rand -base64 24`, затем `ALTER ROLE` | подключение к базе |
| 4 | `YCLIENTS_USER_TOKEN` | повторная авторизация пользователя через API `/auth` | вся выгрузка данных |
| 5 | `YCLIENTS_PARTNER_TOKEN` | кабинет партнёра YCLIENTS → поддержка | то же |
| 6 | `YCLIENTS_OLD_USER_TOKEN` | старый аккаунт — если сверка закончена, оставить пустым | ничего |
| 7 | `DEEPSEEK_API_KEY` | platform.deepseek.com → API keys → создать новый, старый удалить | AI-отчёты |
| 8 | `TELEGRAM_BOT_TOKEN` | @BotFather → `/revoke` | отправка сторис |

Пункт 1 — первый по важности: это доступ ко всей клиентской базе и финансам
барбершопа, а не к API с ограниченными правами.

Менять можно по одному: приложение читает `.env` при старте, после каждой
правки `systemctl restart rubl-director`.

---

## Не забыть, кроме ключей

- **Пароль root на VPS** — он мог уходить в те же руки.
- **SSH-ключ** `id_ed25519_proxy`, если он лежал рядом с проектом.
- **Пароль пользователя `rubl` в PostgreSQL** менять и в базе тоже:
  `ALTER ROLE rubl PASSWORD '<новый>';` — затем то же значение в `.env`.
- **Локальные копии архивов** с боевым `.env` — удалить с диска и из корзины.
- Проверить в YCLIENTS журнал входов на предмет чужих сессий.

---

## Проверка, что старые ключи мертвы

После замены — убедиться, что прежние действительно отозваны:

```bash
# YCLIENTS: должен вернуть 401/403
curl -s -o /dev/null -w '%{http_code}\n' \
  -H 'Authorization: Bearer <старый_partner>, User <старый_user>' \
  -H 'Accept: application/vnd.yclients.v2+json' \
  https://api.yclients.com/api/v1/company/<company_id>/staff

# DeepSeek: должен вернуть 401
curl -s -o /dev/null -w '%{http_code}\n' \
  -H 'Authorization: Bearer <старый_ключ>' \
  https://api.deepseek.com/v1/models

# Telegram: должен вернуть 401
curl -s -o /dev/null -w '%{http_code}\n' \
  https://api.telegram.org/bot<старый_токен>/getMe
```

Если что-то отвечает `200` — ключ живой, отзыв не сработал.

## Чтобы не повторилось

- `.gitignore` теперь исключает `*.zip` и прочие архивы: в них секрет уезжает
  незаметно для code review — именно так утёк пароль кабинета.
- Секреты в репозиторий не попадают даже «как пример»: в `.env.example`
  только заглушки в угловых скобках.
- Перед публикацией репозитория и перед каждым `git add` на файлах
  конфигурации — прогонять `scripts/check-keys.sh` из сборки v2.
